# Agent instructions

Instructions for AI coding agents working on this codebase. Start here for project-wide rules; descend into per-folder `AGENTS.md` (a Folder Contract concept; see [index.md](index.md)) for local conventions.

## Baseline

Rails 8 app. Assume standard Rails conventions unless overridden in this file, a folder-level `AGENTS.md`, or an ADR under [docs/adr/](docs/adr/index.md).

## Safety rules

- **Never push directly to main or merge without explicit user consent.** Always open a PR and wait for approval.
- **Never alter production infrastructure without explicit consent.** Env vars, Render service settings, database operations, deploy triggers — ask first.
- **Never run destructive database commands** (`db:drop`, `db:reset`, `db:migrate`, `db:rollback`, raw `DELETE`/`TRUNCATE`) without explicit user confirmation. See [RULES.md](RULES.md).
- **Never run `bin/rails test`** (or anything that may trigger `db:test:prepare`) without explicit user confirmation — it has side effects.
- **Never take screenshots in agent browser sessions** — use HTML/CSS inspection or describe changes for the user to verify visually.
- **Never edit `app/assets/tailwind/application.css`** — it is autogenerated; put custom CSS in `app/assets/stylesheets/application.css`.

## Checks

Run before pushing or updating a PR:

```bash
bundle exec rubocop -A
bin/rails test     # only with user confirmation per safety rules
```

Prefer `ruby -c` for quick syntax checks over running the full test suite.

### CI

CI runs on GitHub Actions (`.github/workflows/ci.yml`). Status and failures:

```bash
gh run list --limit 1               # latest run status
gh run view <run_id> --log-failed   # failure logs
gh pr checks                        # current PR's checks
```

Common CI failures:

- **Stale branch** — rebase on main when tests pass locally but CI fails on changes from other merged PRs.
- **Rubocop offenses** — always run `rubocop -A` before pushing.
- **Missing keyword args** — view signatures may change after other PRs merge; rebase fixes this.

When amending commits on an open PR, review the PR title and description and update them if scope shifted.

## Git workflow

- Prefer normal commits over amending — keep history navigable.
- Force-push only when explicitly asked.
- When a PR merges and new work is requested, pull the target branch (usually `main`) and create a new branch from it. Confirm before branching if the target might be a feature branch.

### Commit messages and PR titles

[Karma format](https://karma-runner.github.io/0.13/dev/git-commit-msg.html). PR titles use the same format (they become the merge commit).

```
<type>(<scope>): <subject>
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`. Scope is optional — use when clearly scoped to one area (e.g. `feat(diff): add copy buttons`); omit for global changes. Subject: imperative, present tense, lowercase, no trailing period.

Examples:

- `feat(diff): add sticker list diff tool`
- `fix: resolve turbo frame rendering on diff page`
- `refactor(tests): move content assertions to view tests`
- `docs: adopt OKF for project documentation`

## Browser testing (agent sessions)

When using a headless browser to verify UI:

1. App runs on `http://localhost:3000`.
2. Login is email-only — submit the email field and click "Log in".
3. Get a user's slug with `bin/rails runner "puts User.first.slug"` — profiles are at `/u/:slug`.
4. Album cards are inside collapsible sections — click the trigger to expand before inspecting cards.

## Pointers

- **Domain glossary** — [CONTEXT.md](CONTEXT.md). Update inline when introducing or clarifying a domain term; never restate definitions elsewhere. When a user term conflicts with the glossary, call it out.
- **Presentation layer** — UI code lives in `app/ui/` (components, fragments, layouts), not `app/views/`. See [ADR-0006](docs/adr/0006-presentation-layer-organization.md) and [app/ui/AGENTS.md](app/ui/AGENTS.md).
- **Schema** — models own defaults and validations; DB constraints only for race conditions. See [db/AGENTS.md](db/AGENTS.md).
- **ADRs** — managed by [adr-tools](https://github.com/npryce/adr-tools). Check `adr list` before implementing. Suggest a new ADR when a decision is hard to reverse, surprising without context, and the result of a real trade-off. If `adr` isn't installed, create the file manually (next sequential number in `docs/adr/`) and suggest installing adr-tools.
- **Skills** — reusable workflows live in `.agents/skills/`. Suggest extracting one when a multi-step workflow (with decision trees, loops, or conditionals) repeats across sessions. Don't force it — a one-liner doesn't need a skill.

## Knowledge & documentation

Project documentation conforms to [OKF v0.1](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md). Every `.md` file under the repo (except `.agents/`, which is agent-harness config) is an OKF concept: YAML frontmatter with `type` plus recommended `title`/`description`/`tags`/`timestamp`, followed by a markdown body.

We treat the **whole repo as the bundle** (rather than a dedicated `docs/` subtree) so folder contracts stay co-located with the code they govern — agent harnesses pick up `AGENTS.md` from any directory listing without indirection. This stretches OKF's intent (it's primarily designed for curated knowledge corpora, not interleaved with source) but meets §9 conformance. See [ADR-0009](docs/adr/0009-okf-as-documentation-format.md) for the trade-off.

- **Bundle root** — [index.md](index.md) lists every concept; declares `okf_version: "0.1"`.
- **Reserved filenames** — `index.md` (directory listing per OKF §6), `log.md` (history per §7). Don't name concept docs these.
- **Concept types in use** — `Project Overview`, `Agent Instructions`, `Glossary`, `Task Plan`, `Operational Rules`, `Folder Contract`, `Architecture Decision Record`, `Sticker Group`. Pick the closest existing type; introduce a new one only when none fits.
- **Timestamps** — ISO 8601 UTC. Update only when the concept's content meaningfully changes (not for incidental edits).
- **Cross-links** — standard markdown. Bundle-relative absolute paths (`/path/to/doc.md`) are preferred for stability; relative paths are also fine.
- **Discovery** — run `bin/okf` to list all OKF docs with type and description, without reading each file. Use `--type=adr` or `--grep=keyword` to narrow results. Prefer this over reading `index.md` or guessing filenames when you need to find relevant documentation for a cross-cutting change.

### Folder contracts (`AGENTS.md` files)

Each significant source folder carries a co-located `AGENTS.md` of type `Folder Contract` — the local rules for code in that folder ([ADR-0007](docs/adr/0007-adapted-dox-mirror-tree.md), [ADR-0009](docs/adr/0009-okf-as-documentation-format.md)). Co-location means agents see the contract whenever they list the directory.

**Reading**: before editing a file, read the chain of `AGENTS.md` files from the repository root down to the file's folder. The closer doc wins on local details; parent docs set repo-wide rules.

**Updating**: when a change affects a folder's purpose, contracts, conventions, or contents in a way an agent six months from now would want to know, update the nearest `AGENTS.md` in the same commit. Small refactors that don't change contracts can leave docs alone. When a new domain term emerges, update [CONTEXT.md](CONTEXT.md) the same commit.

**Creating**: add `AGENTS.md` to a folder once it has stable local contracts worth recording. Typical body sections: Purpose, Local Contracts, Work Guidance, Verification. Omit empty sections. File-level docs are rare — only when a single file outgrows its folder's `AGENTS.md`.

When you add or move a concept doc anywhere in the repo, link it from the nearest `index.md` (or root [index.md](index.md) for top-level docs).

### Style

- Concise, current, operational.
- Document stable interfaces, non-obvious technical decisions, and information that saves tokens for the next agent. Don't describe what the source code makes obvious.
- Direct bullets with explicit names; no duplication across files unless each scope needs its own version.
- Delete stale notes immediately.
- Prefer soft language ("prefer", "when possible") over strict mandates, except in safety rules above.

## User preferences

When the user requests a durable behavior change ("always do X", "never do Y", "I prefer Z"), persist it immediately in this section or in the relevant folder `AGENTS.md`. Do not wait for the end of the task.

- **Doc-first editing is non-negotiable.** Before writing any source code, read the chain of `AGENTS.md` files for every file you intend to touch. Don't skip this step due to momentum or familiarity.
